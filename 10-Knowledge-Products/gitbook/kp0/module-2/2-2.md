# 2.2 Projects and standing instructions

> **Single message.** Say once, in a project, what you would otherwise paste into every chat: who you are, what you produce, the rules, and the files.

## The concept

A unit that uses an assistant every day starts most chats the same way. It says who it is, what it is working on, which rules apply, and pastes the same files. That is work done again and again, and done a little differently each time, so the answers differ too.

Say it once. Most assistants let you set up a project: a place that holds standing instructions and a set of files, which every chat started in it can see. The instructions are read at the start of every chat in the project, before your first message. The files are there to be read when a chat needs them.

Write the standing instructions as a project brief, the way you would brief a new member of staff. Who the unit is, and the post that owns the project. What the project is for. What the unit produces, and in what format. The standing rules: posts, not names; cite or discard; text in the chat, not files; open questions listed at the end of every draft. What each file is, and its date. What never goes in. And who reviews the brief, and when.

A brief does two things. It makes every chat in the project start from the same place, so answers can be compared. And it writes down the unit's intent, the goals and limits that otherwise live only in people's heads. When the person who set the project up moves on, the brief stays.

Teams that use assistants to write software keep the same kind of brief in a file the assistant reads first, such as one named CLAUDE.md or AGENTS.md. The idea is the same; only the place differs.

## In the tool

Shown in Claude.

Setting up a project. Create a project, give it a name, and paste the brief into its instructions. Add the files: the context pack, the strategy, the template the unit writes to. Then start every chat on that work from inside the project.

Keeping it current. Change the brief when the work changes, and replace a file when a newer version is approved, rather than adding the new one beside the old. Two versions of the same document in one project give two different answers.

Sharing it. In an organisation's account, a project can be shared with colleagues, who then work from the same brief and files. Share it only with the people the files may be shown to.

The blank project brief below is the form to fill. In ChatGPT the same thing is called a project, in Gemini a Gem, and in Microsoft 365 Copilot a notebook.


| Part of the brief | What to write |
| --- | --- |
| Who we are | The unit, its body, and the post that owns this project |
| What this project is for | The work, in one or two sentences, and who it is for |
| What we produce | The outputs, their format, their length and their reader |
| Standing rules | Posts, not names. Cite or discard. Text in the chat, not files. Open questions listed at the end of every draft. Any rule of your own |
| The files | Each file in the project: what it is, its date, and who approved it |
| What never goes in | The kinds of material that must stay out of this project, by name |
| Review | The post that reviews this brief, and the date of the next review |

## Worked example — MoEYS's project brief

*Progressa is the fictional country every course in this knowledge base uses; every body, figure and date in the example is invented.*

The data unit of MoEYS set up a project for the National Learner Registry. Its brief, in full:

Who we are: the data unit of the Ministry of Education, Youth and Skills of Progressa; the project is owned by the head of the data unit. What this project is for: preparing the papers for the National Learner Registry, the single list of learners the Education Sector Plan 2023–2028 calls for, for the Permanent Secretary and the Registry's steering group. What we produce: briefing notes of one page, data-sharing requests, and gap tables; plain English; tables with named columns. Standing rules: posts, not names; every claim about a law, a body or a country with its source, or it is dropped; text in the chat; every draft ends with its open questions. The files: Progressa's country context pack, dated 12 October 2026; the Education Sector Plan 2023–2028; the Data Protection Act 2023. What never goes in: records of learners, even a sample; unpublished cabinet papers; the names of office-holders. Review: the head of the data unit, on the first working day of each quarter.

The first chat in the project asked for a one-page note on the Registry's legal basis. It came back with a table and four open questions, with no names, without being told any of it in the chat.

## Your turn — Draft the standing instructions for your team's project

{% hint style="success" %}
**💡 AI usage tip** · Draft the standing instructions for your team's project

**Bring:** a description of your unit and its work.
**Get:** the standing instructions for your team's project under seven headings, with the points still to be decided.
**Time:** ~20 min · **Assistant:** any; the tips are tool-neutral.
**With the kit:** no skill in this release, so the prompt runs bare in any assistant.
**Watch for:** A wrong rule is repeated in every chat.
{% endhint %}

**The problem it solves.** A team knows how it works but has never written it down for an assistant, so every chat starts again from nothing, and each colleague starts differently.

Copy the prompt, replace the bracketed parts with your own material, and run it in the assistant your organisation has approved. Never paste personal data or unpublished documents: see [1.4](../module-1/1-4.md).

```text
Below is a description of my unit and its work with an AI assistant: who we are, what we produce and for whom, the rules we follow, and the documents we use [paste the description]. Draft the standing instructions for a project our team will share, under these seven headings: who we are; what this project is for; what we produce; standing rules; the files; what never goes in; review. Under 'standing rules', always include: posts, not names; cite or discard; text in the chat, not files; open questions listed at the end of every draft. Under 'the files', list each document I named with a blank for its date and approver. Use only what my description says; where it says nothing for a heading, write 'to be decided' and the question to answer. Output: the brief, under the seven headings, in no more than 400 words, then a list of the points marked 'to be decided'.
```

{% hint style="danger" %}
**Safeguard.** Standing instructions are read by every chat in the project, so a wrong rule is repeated in every answer. The head of the unit reads the brief line by line before it goes into the project, and fills each blank date and approver from the documents themselves.
{% endhint %}
