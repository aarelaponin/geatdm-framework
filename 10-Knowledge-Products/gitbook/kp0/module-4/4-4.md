# 4.4 Judgement: setting up, every day, and what this does not claim

> **Single message.** Set up once, keep a daily routine, and remember what the pattern does not claim: it does not make the work true, cheap or the same every time.

## Try it first — Seven mixed-up moments

*From the record of the registry prototype the course team built for Progressa with the cycle this section teaches. The children's data in it is made up.*

Each moment below breaks one rule of the cycle. Name the rule.


| # | The moment |
| --- | --- |
| 1 | The work chat is still open, so you paste the next step of the work into it. |
| 2 | At the end of the work chat, you ask it to check its own report before you save it. |
| 3 | You paste the report into the chat that helped you write the instruction, and ask it for a verdict. |
| 4 | Memory is on, and the review chat greets you by recalling the work you did this morning. |
| 5 | The review says 'accepted, with minor reservations'. |
| 6 | Your director asks how many pieces of work were accepted this week, and you answer from memory. |
| 7 | Version 2 fails, and you write version 3 with the new gaps added. |

**Your question.** Which rule does each moment break?

<details>

<summary>Answer key: open it after you have tried</summary>

1: one instruction, one piece of work: the next step is a new instruction and a new chat. 2: the one who writes is not the one who checks. 3: a chat never judges work it helped to commission. 4: memory must be off, or the review is not independent. 5: two verdicts, no third word: this is not accepted. 6: status is produced from the log, never remembered. 7: after two failures, write the task again, not version 3.

</details>

## The concept

Set up once. Before the first session you need a folder with three places in it, one each for instructions, reports and reviews; a log; a page of faults for each kind of work you do; and memory off, or an incognito chat for every review. The starter folder holds all of it. After a first cycle, check the setup again against what you actually did.

Then keep a routine. Open the log, and answer where the work stands from it. Pick up the open piece of work with the earliest date: one writes at a time. Read the page of faults before each instruction. Add each new fault a review finds. Hand over before a chat gets long, and before a break.

[Watch for cognitive debt](https://margaretstorey.com/blog/2026/02/09/cognitive-debt/): work accepted that nobody can explain. The cycle makes it easy to accept work, because a review stands behind it. Before you accept, be able to say in your own words what the work found and why the review believed it.

And be clear about what the pattern does not claim. It does not make the output true: a review can miss what the instruction never asked. It does not make the work cheap: it costs a second chat, a log row and your time. It does not make two runs give the same answer. What it does is make every difference discussable, because what was asked, what came back, how it was checked and who decided are all on file, and make every failure countable.

## In the tool

Setting up your computer, from the baseline up. Only the first step is needed. (1) Any assistant in the browser: [the starter folder](../starter-folder/README.md) unzipped, memory off, prompts pasted, replies saved by hand. This works in whatever assistant your organisation approves. (2) The Claude desktop app, on Windows or Mac: chats beside your files, and a project that holds the forms and your page of faults as standing instructions; keep the review chat outside the project. (3) File access, through Desktop Commander or the desktop app's own file extension: the work chat writes its report into the folder and the review chat reads it from there. Allow the starter folder only, never a folder with anything confidential, and turn down any command you did not ask for. (4) Plugins and skills, if your assistant has them. (5) Keep the folder somewhere it is copied, such as a synced OneDrive or SharePoint folder.

Practical tips. Check your organisation's rules before installing anything on a work computer; some organisations do not allow new software or extensions, and then the baseline is the route. Name each chat by piece of work, role and version, such as 'duplicates · review · v2'. Start the review in a new chat every time, version 2 included. Write the log row before you move on.

Sidebar — What automation adds. Everything in this section was done by hand. A plugin can do the bookkeeping: an orchestrator plugin, like the one the course team used to build the registry prototype, starts each work chat and its review chat on a timer, writes the log itself, produces where the work stands on request, and checks that each report names only files it really wrote. It changes nothing in the method. The parallel mistake of 4.1 happened with such a plugin running: automation does the bookkeeping, and the rules stay yours.

## On your work — Write your readiness statement

{% hint style="success" %}
**💡 AI usage tip** · Write your readiness statement

**Bring:** your log and the kinds of work you do.
**Get:** a readiness statement of under 200 words, in three parts.
**Time:** ~15 min · **Assistant:** any; the tips are tool-neutral.
**Watch for:** A statement that promises the cycle for everything.
{% endhint %}

**The problem it solves.** After a course, it is easy to plan to use everything and then use nothing. A short statement of what you will do alone, what you will do with a review, and when you will look again, is a plan you can keep.

Copy the prompt, replace the bracketed parts with your own material, and run it in the assistant your organisation has approved. Never paste personal data or unpublished documents: see [1.4](../module-1/1-4.md).

Two routes: **practise** on the Progressa material in the second tab and check your result against the answer key, or **bring your own** material.

{% tabs %}
{% tab title="Prompt" %}
```text
Below are my log from the cycles I ran in this course [paste it] and a list of the kinds of work I do in a normal month [list them, with how often]. Help me write a readiness statement in three parts. (1) What I now do alone, without the cycle, because none of the five conditions holds: more than three documents; a lasting document; a quoted figure; a change to a file; evidence the assistant cannot see. (2) What I do with an instruction and a separate review, and which page of faults each uses. (3) What I will revisit, and when: a date, and what would make me change the statement. Base it on my log and my list only. Keep it under 200 words. Ask me about anything you cannot tell from them.
```
{% endtab %}

{% tab title="Practise on Progressa" %}
*Invented for this course: every name, number and date below is fictional. Paste it where the prompt asks for your material.*

A head of the planning unit's month: four replies to schools' letters, one census count for the Permanent Secretary, two summaries of donor reports for the unit, one terms of reference for a consultant. Their log: one cycle, the census count, not accepted at version 1, accepted at version 2.

{% endtab %}

{% tab title="Answer key" %}
*Read this after your own run. Your result will be worded differently; check that it finds the same things.*

Alone: the four replies, and the donor summaries kept within the unit. With the cycle: the census count (checking) and the terms of reference (drafting: it lasts and goes outside). Revisit: after the next census, or when a donor summary is first quoted outside the unit. A good statement does not put the replies through the cycle.

{% endtab %}
{% endtabs %}

{% hint style="danger" %}
**Safeguard.** The statement is yours, not the chat's. Strike anything you would not actually do in a busy week; a shorter statement you keep is worth more than a complete one you do not.
{% endhint %}
