## The concept

You have the meaning — the semantic map. The contract — the OpenAPI document. And the data — the gold dataset. Wiring is the step that makes them callable on the bus: registering the service so that a consumer in another agency can discover it and call it. The pattern has a name in the GovStack world — Information Mediation, the building block whose whole job is to mediate exchanges between systems.

'Wired' means three concrete things. The service's description is registered on the provider agency's security server. A consumer in another agency can discover that the service exists. And when the consumer calls it, the request routes through the consumer's security server, across the bus, to the provider's security server, which runs the service and returns the data — all secured across the trust zones you mapped earlier. When that round trip works, the service is genuinely on the bus, not just designed for it.

Three configuration artefacts make wiring real, and you have largely produced them already. The subsystem — the member's registered identity on the bus. The service description — derived directly from your OpenAPI contract. And the access-control list — which other members are allowed to call this service, because being on the bus does not mean everyone may call everything. Registering the member as a subsystem and setting its access-control list is member-onboarding work; here you supply the service description that goes with it.

The GovStack Information Mediation building block is the published pattern for all of this — the reusable specification for the component that routes and mediates exchanges between agencies. Cross-linking your framework to it keeps you aligned with the wider GovStack ecosystem, which matters practically: a vendor's compliant Information Mediator implementation can drop into the role, rather than your country building the mediation component bespoke. That is the re-use principle reaching all the way down to the routing component itself.

And the acceptance here is concrete and runnable — a test call. A consumer's security server calls the service and gets the expected data back, once, over the bus. That single resolving call is the proof that the technical layer works for this exchange: meaning agreed, contract honoured, security enforced, data returned. It is exactly the check the live demonstration runs, and it is the moment the technical-layer configuration stops being a set of documents and becomes a working exchange.

**Service-description notes**

- Type OPENAPI3, service code `identity-api` [confirm]; service version `v1` [confirm].
- Operation exposed: `GET /persons/{nin}`.
- Provider subsystem: `PROGRESSA/GOV/PNIA/IDENTITY` [confirm].

**Access-control entries**

| Service | Subsystem | Decision |
| --- | --- | --- |
| identity-api | PROGRESSA/GOV/PNEA/EXAMS [confirm] | Allow |
| identity-api | PROGRESSA/GOV/PLR/ENROLMENT | Not granted (default deny) |

**Test-call plan**

```text
# 1. Allowed: through PNEA's security server
GET /r1/PROGRESSA/GOV/PNIA/IDENTITY/identity-api/persons/12345678901
X-Road-Client: PROGRESSA/GOV/PNEA/EXAMS
expect: 200, six fields, equal to the record seeded for this test NIN

# 2. Denied: the same call from PLR, through PLR's security server
X-Road-Client: PROGRESSA/GOV/PLR/ENROLMENT
expect: X-Road access-denied fault from PNIA's side

# 3. Not found: a test NIN PNIA does not hold
expect: 404, not an empty 200
```

**GovStack alignment:** the security servers and Central Server fill the Information Mediator building block's role; the r1 path and `X-Road-Client` header are its service-access pattern.

{% tab title="Reading the output" %}
This is the teaching part of the play. Work through the output the way a chief architect would — what is earned, what is invented, what is missing.

<details>

<summary>1. The identifiers and the denial agree with the build pack</summary>

The subsystem names, the service code, the r1 path and the single grant are exactly those in the pack's `manifest.yaml` and its PNIA configuration. The negative call is the pack's own check: PLR is on the bus but holds no grant on `identity-api`. The pack's acceptance record says this denial is observed as an X-Road access-denied fault. A denial that came from a broken connection would prove nothing.

</details>

<details>

<summary>2. The service version was invented</summary>

The run added a service version, `v1`. The pack registers `identity-api` with no version. The "1.0" in the contract is the document's version, not part of the service identifier. A consumer that calls `identity-api/v1` will not reach this service. Strike it, or add it on both sides deliberately.

</details>

<details>

<summary>3. The plan leaves out how the consumer reaches its own server</summary>

The pack's PNEA subsystem accepts only TLS from its own systems; a plain-HTTP call is refused. The test plan should say the call goes over TLS and checks the federation's certificate, never with verification turned off. Otherwise the first test fails for a reason nobody wrote down.

</details>

{% hint style="danger" %}
**Safeguard for this play.** Every member and subsystem identifier must be confirmed against the live X-Road registry before deployment — a wrong identifier does not error clearly, it silently routes nowhere or to the wrong place. Run the test call in a sandbox first, and confirm the access-control list denies a consumer that should not have access, not only that it permits the one that should.
{% endhint %}
