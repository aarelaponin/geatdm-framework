# Module 3 — Design one service as a story your officials can check

**Written for:** the team that has the service specified and built (Architect register). **Videos:** 6.

**What it teaches.** One goal as a story; its failures; its screens with the source of every value; screens officers can use; the walk-through; the review.

**What you can do afterwards.** Have one goal written as a story with its screens, and run the review at which officials agree it.

**What it uses of the worked example.** One goal written in full, the application for a provisional licence, with its screens and walk-through.

## Subtopics

| # | Subtopic | Class | Demonstration | Single message |
| --- | --- | --- | --- | --- |
| [3.1](3-1.md) | One goal, written as a story a builder can follow | Core | — | The builder must not have to work anything out or ask anybody anything. |
| [3.2](3-2.md) | Every way it can go wrong, written down | Core | — | A story is finished only when every failure has its own ending. |
| [3.3](3-3.md) | Screens worked out from the story, every value with its source | Core | — | Each screen serves a step; each value on it says where it comes from. |
| [3.4](3-4.md) | Screens officers can use | Supplementary | — | An officer never types what the system already knows, and never chooses from an endless list. |
| [3.5](3-5.md) | The walk-through your officials click | Core | Yes | The walk-through is produced from the written screens, never drawn by hand, and every page shows its version. |
| [3.6](3-6.md) | The review: three people, every open line given a name | Core | — | The owner, the builder and the person who will live with the result agree the screens; nothing leaves the room unowned. |
