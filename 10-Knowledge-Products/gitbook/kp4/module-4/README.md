# Module 4 — Settle the whole application once, then describe it for the machine

**Written for:** the team that has the service specified and built (Architect register). **Videos:** 6.

**What it teaches.** The interaction design; choosing from long lists by category; the service workflow; the application model; its review; the refusal before generation.

**What you can do afterwards.** Accept the interaction design, including the service workflow, and have the application model reviewed.

**What it uses of the worked example.** The interaction design and the application model of the two applications.

## Subtopics

| # | Subtopic | Class | Demonstration | Single message |
| --- | --- | --- | --- | --- |
| [4.1](4-1.md) | Four questions decided once for every screen | Core | — | How officers pick, find, move and act is settled for the whole application in one document you accept. |
| [4.2](4-2.md) | No list longer than nine: choose by category | Core | — | A long list is divided into categories, and the officer picks the category first. |
| [4.3](4-3.md) | The service workflow: states, moves and who may make each | Core | — | Every state a case can be in, every move between states, and who may make each move, written once. |
| [4.4](4-4.md) | One file a program reads: the application model | Core | — | Everything agreed is carried into one file, from which the application is generated. |
| [4.5](4-5.md) | Reviewing the model: what it assumed, and what it could not express | Core | — | Every assumption and every loss is named for a person to rule on. |
