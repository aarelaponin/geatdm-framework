# 4.4 One file a program reads: the application model

> **Single message.** Everything agreed is carried into one file, from which the application is generated.

## The concept

Your officials have agreed the stories, the screens, the lists and the workflow. All of it now has to reach the platform without anyone retyping it. The method carries it into one file, and a program builds the application from that file.

A low-code platform builds an application from four kinds of part. Forms are the screens where people enter and read values. Lists are the tables of records that people search and open. The user interface, with its menus, leads to each form and list. Processes are the steps of the work. The platform's own documentation describes a builder for each of the four. Find the link in the description.

The usual way is for a builder to click each part together, working from the documents. Every click is a chance to drift from what was agreed. The method does it differently. One file, the application model, holds everything agreed: the records, the lists, the screens, the menus, the workflow, who may do what, and the tests. A program reads the file and generates the parts from it. If something is wrong, the file is corrected, never the parts.

Nothing in the file is new. Each goal's story and its screens become forms and lists. The interaction design you accepted decides how lists, searches, moves and acts behave, and the file names that document. The service workflow becomes the states and moves. The file is written by an AI assistant that must refuse to guess. When something cannot be placed cleanly, it is written down for a person to rule on, not quietly decided.

Here is one section of MoEYS's file, for the goal 'approve a change of an institution's name', read in plain sentences. The minister opens the list of PHEQA's advice on changes of name that waits for a decision. On the screen, the institution's present name is read from PHEQA's register across Linkup, the data exchange, and never copied. The new name and PHEQA's advice come as PHEQA sent them. The decision is chosen, approve or do not approve, never typed. Recording it sends the approval to PHEQA, and officers of MoEYS see it in their list of approvals.

The file is written for a program, not for you. So ask the supplier for a plain-sentence reading of each section, beside the file. Your officials check the reading against the screens they agreed. Then the business side and the builder read the same thing, and a decision means the same in both rooms. Keep one thing in mind: where the reading and the file differ, the file is what gets built. Raise every difference before the file is approved.

## Your turn — Read one section of the model in plain sentences

{% hint style="success" %}
**💡 AI usage tip** · Read one section of the model in plain sentences

**Bring:** One section of the model and the agreed screens of its goal.
**Get:** A plain-sentence reading of one section, with anything not agreed marked, and the differences listed in both directions.
**Time:** ~10–15 min · **Assistant:** any; the tips are tool-neutral.
**With the kit:** `application-model` — helps the team write the one file a program reads, and the review of what it assumed and could not express. Optional: the tip runs bare; see [the kit](../../start-here/ea-plays-kit.md).
**Watch for:** The reading is an explanation, not the file.
{% endhint %}

**The problem it solves.** The supplier has written the application model, a file meant for a program. Before it is approved, the official who owns a goal needs to read what that goal's section will build, in words, and to see anything in it that was never agreed.

Copy the prompt, replace the bracketed parts with your own context, and run it in the AI assistant of your choice. Never paste personal data or unpublished documents — see [How to use the plays](../../start-here/how-to-use-the-plays.md).

```text
Below is one section of an application model for [your ministry], the part that covers the goal [name of the goal] [paste the section]. Below that are the screens of that goal as your officials agreed them [paste them]. Explain the section in plain sentences for an official who has never read such a file: what list the person starts from, what each screen shows and where each value comes from, what the person decides and how, what happens when it is recorded, and who may do each thing. Use the words of the agreed screens wherever they exist. Then compare the two: list every thing in the section that the agreed screens do not contain, and every thing in the screens that the section leaves out. Do not correct either. Output: a plain-sentence reading of one section, with anything not agreed marked, followed by the two lists of differences.
```

{% tab title="Reading the output" %}
This is the teaching part of the tip. Work through the output the way a chief architect would: what is earned, what is invented, what is missing.

<details>

<summary>1. The effective date is caught</summary>

The file sets a date the change takes effect, and the screens never mention one. The run marked it in the reading and listed it. That is the same assumption the review of the model must put to the Director of Higher Education in [4.5](./4-5.md).

</details>

<details>

<summary>2. The reading says what was agreed, not what the file says</summary>

The file reads `present_name text source: form`: a box someone types into. The reading says the present name is read from PHEQA's register across Linkup, because it used the agreed screens' words. The difference list missed it. The file is what gets built, so this one goes to the person who approves the model, not into a corrected reading.

</details>

<details>

<summary>3. "Officers see it" is thinner in the file</summary>

The screens say officers of MoEYS see the approval; the file grants only the role "minister" and says nothing about who may read the list. Ask whether that was meant.

</details>

{% hint style="danger" %}
**Safeguard.** The reading is an explanation, not the file. Check it against the agreed screens; where the reading and the file differ, the file is what will be generated, so every difference goes to the person who approves the model and is never settled by changing the reading.
{% endhint %}
