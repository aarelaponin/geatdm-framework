# 3.2 Five tiers between a messy file and a trusted record

> **Single message.** Data reaches the register through five tiers, raw, bronze, staging, silver and gold, with quality checks at bronze and a person's approval before silver.

## The concept

Every term, schools send lists of learners. Some are spreadsheets, some are exports, some were typed from paper. Column names differ. Dates are written three ways. Write such a file straight into the register, and the register becomes one more list nobody trusts.

UNICEF Giga publishes a flow for school data that solves this. It has five tiers. Raw is the file as it arrived, with wrong column names and wrong data types. At bronze, the columns are mapped, the quality checks run, and the rows are split into two tables: those that passed and those that failed. At staging, a person with the right permission approves or rejects each passed row. Approved rows are merged into silver. Silver is merged into gold, which is split into a master table and a reference table.

Two things in this flow are easy to get wrong. First, raw is a tier of its own, and the checks run at bronze. The file is kept as it came, so you can always show what a school sent. Second, a person approves the rows before they reach silver. That approval is an act of responsibility. A program can prepare it, but it cannot replace it.

Giga says its tiers were inspired by a common data pattern, which Databricks describes as layers that improve the structure and quality of data step by step. The GovStack Digital Registries specification does not describe tiers. It does let you keep several linked databases in one installation, and run scheduled, rule-based automation that moves records between them. So the tiers can be held as linked databases beside the register, or in a data platform in front of it. Applying Giga's school flow to learners is this course's own adaptation.

Here is what a good run of this walkthrough shows. A seeded file of Progressa learners, with some faulty rows in it, enters raw. At bronze, the faulty rows go to the failed table. At staging, an officer of the learner registry approves the passed rows. The count of rows is read at every tier. A good run passes when only approved rows reach silver and gold holds the master records.

## Your turn — Design the five tiers for a new source file

{% hint style="success" %}
**💡 AI usage tip** · Design the five tiers for a new source file

**Bring:** The header row and invented sample rows of one source file, with the register's schema.
**Get:** A tier design table with the column mapping, the bronze checks and the staging approver, and a list of open questions.
**Time:** ~10–15 min · **Assistant:** any; the tips are tool-neutral.
**Watch for:** The approval at staging is a person's act and is not replaced by the prompt.
{% endhint %}

**The problem it solves.** Each new body that sends learner data sends it in its own shape. This prompt designs how one source file passes through the five tiers: how its columns map, which checks run at bronze, and who approves at staging.

{% tabs %}

```text
Below are the header row and ten invented sample rows of a file that [name of the sending body] will send to our learner register [paste], and the register's schema [paste]. Design the five tiers this file passes through: raw, bronze, staging, silver and gold. (1) Map every source column to a schema field, or mark it to be dropped; list the schema fields the file lacks and say whether each may be empty. (2) List the checks to run at bronze, one row per check: the field, the rule, whether a failure is critical, and the message the sender will read. (3) Name the role that approves rows at staging and what that person looks at before approving. (4) Say what moves from silver to gold and into the register. Mark every guess for confirmation. Output: a tier design table with the column mapping, the bronze checks and the staging approver, then a list of open questions.
```

**Tier design for the district term list (draft)**

| Tier | What happens | Detail |
| --- | --- | --- |
| Raw | The file is kept as sent | No change to any value |
| Bronze: mapping | Columns mapped | SchoolCode → school_code; PupilName → given_name; Surname → family_name; DOB → date_of_birth; Sex → sex (F/M → female/male); Class → grade (P4 → 4, *guess*); DateAdmitted → enrolment_date. Dropped: AdmNo, Remarks. Lacking: pnia_service_identifier and guardian identifier (may be empty); status (required, *guess: "enrolled"*) |
| Bronze: checks | Critical: required values, date written two ways, sex in the list, grade 1–12, age fits the grade, school exists | Message, for example: "The date is not written as year-month-day. Write it as, for example, 2015-03-21." |
| Staging | A PLR registry officer approves or rejects each passed row | Looks at possible matches with existing learners, and at the bronze report |
| Silver → gold | Approved rows merged; gold split into master (learners) and reference (schools, code lists) | Master records go into the register; the register gives each new learner a number |

**Open questions**

- Does "Class" always mean a primary grade, or do secondary schools send "F1"?
- May status be set to "enrolled" when the file does not say?
- How is a learner already in the register recognised, when the file carries no learner number?
- Is "repeat" in Remarks a fact the register should hold?
{% endtab %}

{% tab title="Reading the output" %}
This is the teaching part of the tip. Work through the output the way a chief architect would: what is earned, what is invented, what is missing.

<details>

<summary>1. The mapping and the approver follow the schema</summary>

Every source column is mapped or dropped, every schema field the file lacks is named, and the approver is a person, a PLR officer, as the tier layout specimen sets. The guesses are marked.

</details>

<details>

<summary>2. A default value is a quiet invention</summary>

Setting status to "enrolled" for every row writes a fact no school sent. It is marked as a guess, but a tired reviewer would accept it. The owner should decide; the safer rule is to ask the sender for it.

</details>

<details>

<summary>3. Matching is the hard part, and it is left open</summary>

Without a learner number in the file, the duplicate check cannot run on the key. The run lists the question but proposes no rule for matching on name, date of birth and school. That rule decides how many duplicates reach staging, and the owner must set it.

</details>

**Safeguard.** The approval at staging is a person's act and is not replaced by the prompt. Never paste real learners' records into the prompt; use the header row and invented sample rows.
