# KP2 build pack — plan: the missing M4 / M5.2 / M5.3 artefacts

**Date:** 3 August 2026
**Addresses:** rows M4, M5.2 and M5.3 of `KP2_Build_Pack_Fitness_Review_2026-08-03.md` §1
**Companion to:** that review's workstream W1 (this plan is W1, specified)

## Objective

Close three of the four gaps between what the KP2 modules say the build pack contains and what is on disk:

| Gap | Promised by | Becomes |
|---|---|---|
| No semantic map artefact | M4.4 | `configs/semantics/` — and the single source of truth for every field list in the pack |
| X-Road service descriptions only implicit | M4.5, M4.7 | `configs/services/` — the derived form, explicit and checked |
| No Member Requirements checklist | M5.2 | `configs/onboarding/member-requirements/` — template + four filled instances |
| No SLA template | M5.3 | `configs/onboarding/sla/` — template + three filled instances |

## Decisions taken (3 August)

1. **The semantic map is load-bearing, not documentary.** It becomes the single source of truth for the field lists currently copied in five places.
2. **Member Requirements and SLA ship as template + filled instances** for the four canonical members and the three published services. No coupling to module 2.7's join API (its scope is unresolved).
3. **These artefacts enter `manifest.yaml` under a new `foundation:` block**, not as new modules — they are layer artefacts, not deployment steps, and their acceptance is a document check rather than a live check.

Decision 3 diverges from the `kp-build-pack` anatomy KP3/KP4 share. §5 below handles the consequence.

## 1. Design — the semantic map as source of truth

### 1.1 The problem being solved

The same field list exists in five places today, with nothing keeping them equal:

| Copy | Location |
|---|---|
| Config fragment | `configs/member-plr/2.4.yaml` `semantic:` block ("from the Module 4 semantic map"), same in `2.5.yaml` |
| Published contract | `apps/specs/*.openapi.yaml` response schemas + enums |
| Exchange declaration | `configs/x-road-bus/2.6.yaml` `asked_once` |
| Acceptance assertion | `scripts/acceptance.sh:259-261`, a bash-embedded Python set literal |
| Seed data | `scripts/gen_seed_data.py` CSV columns and value pools |

Three of these already claim to derive from "the Module 4 semantic map" — an artefact that has never existed. `prompts/2.4.md` and `prompts/2.5.md` instruct the model to paste it in. The map is not a missing document; it is a **dangling reference that four artefacts already depend on**.

Code lists are the sharpest instance. `sex: enum [F, M]` and `status: enum [active, transferred, completed]` live only in the OpenAPI specs, while `gen_seed_data.py` picks values from independent Python lists. Nothing today would catch a seed value the published contract does not allow.

### 1.2 The artefact

`configs/semantics/learner-credential.map.yaml` — one map per exchange, per M4.4's "for a single exchange, sets out five things". Six elements, not five: the pack's live purpose-limitation behaviour needs a sixth.

| Element | M4.4 name | Content here |
|---|---|---|
| 1 | entities | `person` (PNIA), `enrolment` (PLR), `school_record` (MoEYS/PEMIS) |
| 2 | fields | per entity: name, type, ISO/IEC 11179-style definition, vocabulary alignment (OneRoster / CEDS term) |
| 3 | code lists | `sex`, `enrolment_status`, `region`, `level` — allowed values, with each agency's local values mapped |
| 4 | identifier | `nin`, 11 digits, `[confirm: exact NIN format]`, plus the merge risk M4.4's safeguard names |
| 5 | mapping | each agency's own term → the shared definition |
| **6** | **release sets** | **per purpose, which fields the contract publishes** — e.g. purpose `credential-application` releases 6 of the 9 person fields; `mother_name`, `birth_registration_no`, `residence_address` are **held** |

Element 6 is what makes the map load-bearing rather than descriptive. `apps/mock-registry/app.py` already filters every response to exactly the OpenAPI spec's declared fields and exposes withheld field *names* at `/held-fields`. The map is where that release decision is recorded and justified (M4.8's data-protection envelope), instead of being implicit in which fields someone happened to type into a spec.

### 1.3 The derivation chain — two different mechanisms, deliberately

```
configs/semantics/learner-credential.map.yaml          ← THE SOURCE
        │
        ├── DERIVE-AND-CHECK  (generated by the AI play, then proven equal)
        │     ├── apps/specs/*.openapi.yaml            response schemas, enums, required[]
        │     └── configs/services/*.xroad.yaml        the X-Road service description (§2)
        │
        └── READ AT RUNTIME   (no copy exists at all)
              ├── configs/x-road-bus/2.6.yaml  asked_once      → read from the map
              ├── scripts/acceptance.sh:259-261               → read from the map
              ├── configs/member-*/N.yaml  semantic: blocks   → read from the map
              └── scripts/gen_seed_data.py  columns + pools   → read from the map
```

**Why two mechanisms.** The OpenAPI contract must stay a *generated artefact of the `gif-openapi-gen` play* — M4.5 teaches precisely that move ("give Claude the service brief and the semantic map; it drafts the OpenAPI document"). Replacing that with a Python generator would delete the teaching. So the spec is generated by the prompt, committed, and then **proved equal to the map by a checker** — the same shape `hurl/check_scenarios.py` already uses for scenarios vs configs.

Everything downstream of the contract, however, is machine plumbing that no video teaches. Those copies should not exist at all; they should read the map.

### 1.4 Why this is the same fix as the hard-coding finding

Closing the M4 gap and closing the review's finding §3.1 are one piece of work. `acceptance.sh:259-261` stops restating ten field names because there is finally a canonical place to read them from. That is the argument for doing this first.

## 2. Design — X-Road service descriptions made explicit

M4.5 and M4.7 both teach "one contract, two forms": OpenAPI for humans and tools, the X-Road service description for the bus to route. In the pack the second form exists only as behaviour — `hurl/templates/fragments/SERVICE_PUBLISH.hurl.tmpl` posts a `spec_url` and X-Road parses it. A learner following M4.7 has nothing to look at.

`configs/services/<member>-<service>.xroad.yaml` makes it an artefact: service code, description type (OPENAPI3), the spec URL, the published operations, the ACL subjects, and the mapping from each OpenAPI operation to the X-Road service code it becomes. Derived from the OpenAPI document, checked against it, and checked against the ACL already in `configs/member-*/N.yaml` — so a service published with an ACL the service description disagrees with is a `--fast` failure rather than a live surprise.

This is a **documentation-of-existing-behaviour** artefact. It must not become a second input to `hurl/generate.py`; generation keeps reading `configs/member-*/N.yaml`, and the service description is checked against it. Introducing a second write path into the deploy sequence is explicitly out of scope.

## 3. Design — Member Requirements (M5.2) and SLA (M5.3)

### 3.1 Template + instances

`prompts/2.2.md` through `2.5.md` already carry the precondition line *"PLR has passed the Member Requirements checklist (Module 5.2) and its service levels are set in a signed SLA (Module 5.3)"*. Second dangling reference. The artefacts are already load-bearing in the pack's own prose.

```
configs/onboarding/
├── member-requirements.template.yaml     ← the reusable blank (M5.2's six items)
├── member-requirements/
│   ├── moeys.yaml  pnea.yaml  plr.yaml  pnia.yaml     ← four filled instances
├── sla.template.yaml                     ← the reusable blank (M5.3's six fields)
└── sla/
    ├── pnia-identity-api.yaml  plr-enrolment-api.yaml  moeys-pemis-api.yaml
```

**Member Requirements**, per M5.2's slide 2 — six objective yes/no items, each with what "met" looks like and the evidence: a security server; a registered identity (subsystem); the standards portfolio adopted; data cleaned and conformed to the schema (evidence: conforms to the §1 semantic map — this is where the two workstreams meet); a lawful basis per exchange, citing the decree article; a named technical contact and incident channel. Plus the readiness verdict block.

**SLA**, per M5.3's AI prompt — availability, response time, support hours, incident response by severity, change-notice period, reporting. Each field carries a **pilot value and a production value**, and `[confirm: agree with provider]` on every number, because M5.3's own safeguard says the value is not real until the provider agency agrees it. The production column feeds `docs/production-delta.md`.

### 3.2 What the acceptance checks assert

Both are document checks (`--fast` tier, no stack):

- **Member Requirements:** every member in `manifest.yaml`'s `identity.members` with `origin: canonical` has an instance; every instance has all six items with a verdict; every "lawful basis" item names a decree article; every "data conformed" item names an entity that exists in the semantic map. A member registered on the bus with no passed checklist is a failure.
- **SLA:** every service published in any `configs/member-*/N.yaml` has an SLA instance; every instance has all six fields with both a pilot and a production value; every unresolved value is a visible `[confirm: agree with provider]` rather than an invented number.

The second half of each check is the interesting one: it ties the organisational layer to the technical configuration that already exists, so the two cannot drift apart silently.

### 3.3 Deliberately not doing

No join-API gate. Wiring Member Requirements into `apps/join-api`'s validation would make the organisational layer genuinely gate onboarding — but it couples this work to module 2.7, whose scope is the largest unresolved question in the review. Revisit once 2.7's fate is decided.

## 4a. Precondition — a clean, self-consistent base

Confirmed 3 August against `github.com/aarelaponin/geatdm-framework`: the pack is version controlled (257 tracked files, branch `itu-presentation-skills-files`), so the destructive tasks below — A5's rewrite of `acceptance.sh`, A7's change to seed generation, A8's golden-corpus regeneration — are all recoverable. No `git init` precondition applies.

One thing does block A2 and A4:

- `configs/member-ptsb/` is **untracked** and `manifest.yaml` is **modified** — the 3 August PTSB join is uncommitted local state. Commit or discard it before authoring the map, so A2 is generated against a base that is what a checkout gets.
- `apps/specs/ptsb-awards.openapi.yaml` **is tracked** while its config is not. This directly breaks **A4**, whose checker scans `apps/specs/*.openapi.yaml` and would demand an `award` entity the map has no reason to carry. Resolve by one of: (a) untrack the spec with the rest of the PTSB residue (aligns with the review's W2); or (b) scope A4's glob to specs referenced from `configs/member-*/*.yaml`, which is more robust anyway and survives the next join. **(b) is the recommended fix; (a) is the recommended cleanup. They are not alternatives — do both.**

The same asymmetry means **D5's SLA rule needs the filter C5 already has.** C5 scopes to `origin: canonical`; D5 as drafted says "every service published in any `configs/member-*/N.yaml`", which today catches nothing (PTSB publishes no services) but would demand an SLA for a demonstration artefact the moment a joined member publishes one. Add the `origin: canonical` filter to D5.

## 5. Sequencing

```
A1 → A2 → A3 → A4 ─┬─→ A5 → A6 → A7 → A8
                   ├─→ B1 → B2 → B3 → B4
                   └─→ C1..C5 ∥ D1..D6
                                    └─→ E1..E5
```

- **A2 before everything.** B, C and D all cite the map; generating them first means regenerating them.
- **A4 before A5.** Land the checker before changing read paths, so the first thing that proves the map correct is not the acceptance suite failing.
- **C and D are independent of B** and can run in parallel; neither touches the running stack.
- **E last**, once every path it indexes exists.

Two natural checkpoints: after A8 (the semantic layer is real and load-bearing) and after E5 (the pack's index shows three layers). Each is a sensible place to stop.

## 6. Cost and risk

| | Estimate | Risk |
|---|---|---|
| A (semantic map) | The bulk. A5–A7 touch working code. | **Medium.** A7 changes seed generation, which every acceptance check reads. Mitigation: A7 is the last A-task, gated on `--full` under `profile: lite`; keep the current CSVs until the generated ones are byte-compared. |
| B (service descriptions) | Small. | **Low** — read-only artefact. The one real risk is scope creep into the deploy path; §2's "must not become a second input to `generate.py`" is the guardrail. |
| C + D (onboarding) | Moderate, mostly authoring. | **Low.** No code paths touched. The temptation to invent SLA numbers is the actual risk — `[confirm:]` discipline is the control, and `check_pack.py --ready` enforces it. |
| E (wiring) | Small. | **Low**, but E3's upstream propagation is a cross-pack coordination item, not a code change. |

Net effect on `--fast`: three new checkers. Keep them under ~2 s combined — the review already flags that tier's growth from 8 s to 49 s as compounding, since `--full` runs it inside the reproducibility proof.

## 8. Definition of done

- `configs/semantics/`, `configs/services/` and `configs/onboarding/` exist, each generated by a committed prompt in `prompts/`, none hand-fabricated.
- No field list, code list or release set is stated twice anywhere in the pack; the five copies in §1.1 are one source plus checked derivations.
- `scripts/acceptance.sh` contains no literal field names.
- `manifest.yaml`'s `foundation:` block resolves for every entry, and `check_pack.py --ready` still exits 0 with the new checkers running.
- `verify.sh --full` green under `profile: lite`, then once under `full`.
- Every M4.4, M4.5, M4.7, M5.2 and M5.3 viewer can open the artefact their video describes.
