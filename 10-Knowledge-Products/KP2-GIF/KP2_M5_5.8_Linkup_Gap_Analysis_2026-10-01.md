## 2. Build-pack work

### WP-A `scripts/opmon-export.sh`: metadata-only operational data, refused if anything personal is left

1. **Route.** Call each Security Server through its own client port, the same way `xroad.py`'s `exchange()` does. The host ports are 1080, 2080, 3080 and 5180, or 8443 with the exchange TLS context where the client is TLS-only. Issue `getSecurityServerOperationalData` with a `recordsFrom`/`recordsTo` window. Implement it as a small Python module, not a Hurl step: it needs MTOM/multipart parsing and gzip decoding.
2. **Who may read what (decision D2).** The owner of a Security Server, or a configured *central monitoring client*, gets every record. Any other client gets only its own records. Two options:
   - (a) Four queries, each made by that server's owner member: PDGA on ss-pdga, PNEA on ss-pnea, PLR on ss-plr, PNIA on ss-pnia. This works with today's identities.
   - (b) Make `PROGRESSA/GOV/PDGA:MANAGEMENT` the federation's monitoring client on the Central Server and query everything as the Operating Authority. This is closer to production and tells a better story ("the Operating Authority watches the bus"), but it is a Central Server configuration step to prove first.

   Default: **(a) now, (b) as a named follow-up.**
3. **Normalise.** Each exchange is logged twice, once on the client-side server and once on the producer-side server. Join the two on `messageId` into one row with both durations. Drop the export's own `getSecurityServerOperationalData` calls.
4. **Allow-list, never deny-list.** Keep:
   - the timestamp, as relative time `T+mm:ss` when `--relative` is set, so the capture is stable;
   - the client and service identifiers, the service code and the REST method;
   - `restPath` **templated back to the contract path** (`/persons/{nin}`), using `apps/specs/*.openapi.yaml`;
   - `succeeded`, the status code, the fault code and the request and response sizes;
   - total and producer-side duration.

   Drop everything else: `messageUserId`, `messageIssue`, `representedParty*`, every IP and address field, and `faultString` (it can echo the path).
5. **The guard.** Before anything is written, scan every value in the export for any NIN or name present in `apps/data/*.csv`. On a hit, exit non-zero and name the field, not the value. This is "never the cargo" turned into a check.
6. **Output.** Write `out/opmon/opmon-<run>.jsonl` and an `export.json` header recording the window, the servers queried, the record counts before and after the join, the pack commit and the X-Road version.
7. **Tests** (`tests/test_opmon_export.py`, offline):
   - a fixture record with the NIN in `restPath` comes out templated;
   - a fixture with an untemplatable NIN-bearing field makes the export refuse;
   - the client/producer join and the self-call filter.

### WP-B `scripts/opmon-traffic.sh`: a scripted "week in miniature" with known incidents (demo only)

Refuse under `posture: production`, matching the P1 pattern. Use a fixed schedule and fixed NINs, so the call **counts** are identical from run to run even though timings vary.

| Incident | How it is injected | What the data should show |
|---|---|---|
| Baseline | PNEA runs the once-only pair (identity + enrolment) for the seeded learners at a steady rate for ~6 min | ~100% success; a stable p95 |
| **I1 outage** | `docker stop app-plr` for ~60 s, then start it | A burst of enrolment-api failures; identity-api unaffected (the 5.6 lesson seen from the operator's side) |
| **I2 slowdown** | A **demo-only delay knob** on the mock registry, e.g. `POST /v1/_demo/delay` enabled only when `KP2_DEMO_FAULTS=1`, on PNIA for ~90 s | identity-api p95 rises while success stays 100%: the "creeping slowdown" |
| **I3 unexpected caller** | PLR:ENROLMENT calls identity-api, as in C5: AccessDenied | A caller/service pair never seen in the baseline |
| **I4 spike** | 150 calls from PNEA in 30 s | Per-minute volume far above the baseline |
| "3 a.m. surge" | **Not reproducible.** Op-monitoring timestamps are real and cannot be backdated honestly | Keep it as a spoken example only, or see D4 |

The script writes `out/opmon/incidents.json` as the ground truth: what was injected and when, in the same relative time. It finishes with the delay knob off, app-plr healthy, and `acceptance.sh --only 2.6` green.

### WP-C `scripts/opmon-report.py`: deterministic health table, and the check on the AI's flags

- **The health table.** Per service: calls, % failed, p50 and p95, per window. Caller/service pairs first seen after the baseline. Minutes whose volume is more than three times the baseline median. This is pure arithmetic over the export, with no AI. It is what the human compares against.
- **`--check <report.md>`.** Every number Claude states must match the table within a tolerance. Every incident in `incidents.json` must be flagged. Any flag with no matching incident is listed as a **false positive**, which is not an error. It is the "question for a human, not a verdict" safeguard, made visible.

### WP-D the play: `prompts/bus-monitoring.md`

- Base it on the §3.8 AI tip, with the input renamed to "operational monitoring data (the WP-A export)". Add one line saying the message log is never an input.
