## Reading the output

### 1. The pilot column is the build pack's

The pilot values are the five terms in `onboarding/plr/03-sla/enrolment-api.md`, and PNIA's file carries the same ones: one template, reused for every service. The model also kept the rule from B17 that a consumer signs none. That matches the pack, where PNEA's SLA gate is marked out of scope because it publishes nothing.

### 2. "Response time" means two different things

The pack's response-time term, "4 business hours; 1 hour for a P1", is how fast support responds. The page and the prompt mean how fast a call returns. The run kept the pack's wording in the pilot column and wrote call latency in the production column, so the row compares two different measures. Split it into two fields. The production numbers are invented; none of them has been discussed with PLR.

### 3. Nothing yet proves the levels

The reporting row is the weakest. The pack's monitoring add-ons run on every Security Server, but no central collector receives their data, and the pack lists that as a gap. Its SLA values are also marked illustrative, not a real signed target. Until monitoring data reaches PDGA, a 99.5% commitment can be signed but not checked.
