## Example input

The exchange, from the Use-Case Catalogue (B5), first-wave row PNIA → PNEA: identity: when a learner applies for a senior-secondary certificate, PNEA's examination system asks PNIA for the learner's identity by National ID number (NIN). PNIA returns given name, family name, date of birth, sex and region. Nothing else.

The edge, from the component-to-layer map (B20): PNEA (subsystem EXAMS) and PNIA (subsystem IDENTITY) each run their own security server. Certificates come from the Linkup pilot's test certification authority. The call is `GET /persons/{nin}` on PNIA's `identity-api`.

## Example output

| Segment | Zone | Control required | Held by |
| --- | --- | --- | --- |
| PNEA examination system → PNEA security server | Member-Internal (PNEA) | TLS on the internal hop; caller names itself as `PROGRESSA/GOV/PNEA/EXAMS` | PNEA security server |
| PNEA security server → PNIA security server | Public | Mutual TLS; message signed under X-Road's protocol | Both security servers |
| PNIA security server → PNIA identity service | Member-Internal (PNIA) | Access-control check (only PNEA:EXAMS may call); TLS on the internal hop | PNIA security server |
| Identities at both ends | Trust-Anchor | Valid, unrevoked certificates from the federation's CA; OCSP status checked | CA and OCSP responder |
| Audit record | — | Correlation id, sender, recipient, service, signature, timestamp; log sealed at intervals | Message log on each security server |

**How this could fail**

- A certificate at either end is expired or revoked and nobody notices.
- PNIA's identity service can be reached directly, not only through its security server.
- The certification authority signs requests without checking who is asking.
- PNIA's access-control list grants more subsystems than PNEA:EXAMS.

## Reading the output

### 1. The public-zone row is earned

Mutual TLS, a signed message and an audit record on both sides: this is what X-Road gives every call between security servers, and it matches the input. A security reviewer can accept that row as written.

### 2. Both internal hops are assumed, not known

The run asks for TLS inside each member's network, but nothing in the input says so. In the build pack the hop from PNIA's security server to its service is still plain HTTP, and PNEA's hop is encrypted but the calling system does not present a certificate of its own. "Internal" is not the same as "safe". Write down what each hop actually does before the trace is filed.

### 3. The third failure mode is already true in the pilot

A test CA signs any request with no vetting. The pack records this as a simulated gate, not a passed one. So for production the Trust-Anchor row depends on a procurement decision that has not been taken yet. Carry it into the Member Requirements as a condition of go-live.
