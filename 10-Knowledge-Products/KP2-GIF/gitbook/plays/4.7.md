## Example input

**Contract (B24):** PNIA identity API, OpenAPI 3.0.3, one operation: `GET /persons/{nin}` returning `nin`, `given_name`, `family_name`, `date_of_birth`, `sex`, `region`; 404 if no person.

**Provider:** PNIA, subsystem IDENTITY, on its own security server. **Consumer:** PNEA, subsystem EXAMS.

**From the tier map (B6):** PNIA and PNEA are both Champions and onboard first, with PDGA operating.

**Access policy:** only PNEA's examination subsystem may call this service. PLR is also a member, as a provider of enrolment data, but has no reason to read identity records.

**Identifiers:** instance PROGRESSA, member class GOV.

## Reading the output

### 1. The identifiers and the denial agree with the build pack

The subsystem names, the service code, the r1 path and the single grant are exactly those in the pack's `manifest.yaml` and its PNIA configuration. The negative call is the pack's own check: PLR is on the bus but holds no grant on `identity-api`. The pack's acceptance record says this denial is observed as an X-Road access-denied fault. A denial that came from a broken connection would prove nothing.

### 2. The service version was invented

The run added a service version, `v1`. The pack registers `identity-api` with no version. The "1.0" in the contract is the document's version, not part of the service identifier. A consumer that calls `identity-api/v1` will not reach this service. Strike it, or add it on both sides deliberately.

### 3. The plan leaves out how the consumer reaches its own server

The pack's PNEA subsystem accepts only TLS from its own systems; a plain-HTTP call is refused. The test plan should say the call goes over TLS and checks the federation's certificate, never with verification turned off. Otherwise the first test fails for a reason nobody wrote down.
