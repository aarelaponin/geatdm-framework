# Golden path — the skill pack, end to end

This is a **worked reference**: the whole skill chain run on Progressa fixtures to produce a complete
platform repo, so the team can see the entire build → catalogue → consume → go-live loop in one place
rather than as 13 separate demos. Everything in `platform-repo/` was generated by the skills' own
scripts — nothing hand-written except the small input specs in `inputs/` and the fixture in
`fixtures/school-census/`.

**Simulated case.** Progressa is the fictional country of the courses. PEMIS (its education
management information system), the examination authority PNEA, and every
school, table, column and figure here are invented.

## Run it yourself

```bash
cd kit/golden-path
bash run_golden_path.sh          # macOS / Linux; pure Python (PyYAML for one step), no database needed
bash run_golden_path.sh /tmp/gp  # or name the output folder
```
Step 4 reads the School Census fixture in `fixtures/school-census/` — `census.pbl`, a synthetic
stand-in for a PowerBuilder library (it holds only the text the extractor reads: DataWindow definitions
and embedded SQL, encoded UTF-16LE as a real library stores them), and `pemis_inventory.yaml`, the
schema inventory. Set `PB_MODULE` / `PB_INVENTORY` to point at a real module instead. The run writes
its own `platform-repo/` and `readiness.yml` into `out/` beside this file, or into the folder you
name; it never writes over the committed example, `platform-repo/` and `readiness.yml` here, which
are the output of the same run. To refresh the example after changing an input, run into an empty
folder and copy its two outputs over the committed ones.

## What each step produced (the loop)

| Step | Skill | Output in `platform-repo/` |
|---|---|---|
| 1 | `repo-scaffold` | the mono-repo skeleton + conventions + `.pre-commit-config.yaml` + `tasks.py` |
| 2 | `onboard-source` | `ingestion/pemis/bronze_pemis.sql` — Bronze DDL, money widened to `Decimal(38,2)` |
| 3 | `import-schema-to-catalogue` | `dbt/models/_sources/pemis__sources.yml` (the three PEMIS tables: school, district, censusreturn), `catalogue/import/pemis_technical.yaml`, `catalogue/vocabularies/learner_status.yml` |
| 4 | `legacy-module-to-openmetadata` | `catalogue/module-semantics/School_Census_OpenMetadata.{yaml,md}` + `_extraction.json` (the script's DRAFT scaffold; the finished enrichment is in the skill's `references/school-census-worked-example.md`) |
| 5 | `build-dbt-model` | `dbt/models/staging/stg_pemis__{school,district,censusreturn}`, `intermediate/int_school__master` (golden record + join contracts), `marts/mart_school__enrolment_summary` |
| 6 | `add-dq-checks` | `dbt/models/_dq/mart_school__enrolment_summary.dq.yml` + singular tests + `quality/thresholds/...` |
| 7 | `build-superset-dashboard` / `expose-api` | `consumption/dashboards/school_enrolment/*`, `consumption/api/enrolment_*` |
| 8 | `onboard-consumer` | `consumption/consumers/pnea_exams/{onboarding_plan.md,gap.json}` (the examination authority served by reuse) |
| 9 | `production-readiness-check` | `ops/readiness_report.md` — **GATE PASS** |

## What to look at first

- **`dbt/models/intermediate/int_school__master.sql` + `.yml`** — the School-360 golden record:
  the join is a named model, and its key carries `not_null` + `relationships` tests (the join
  **contract**). The mart composes from it; it never re-joins raw sources.
- **`catalogue/module-semantics/School_Census_OpenMetadata.yaml`** — what a legacy module's data
  meaning looks like recovered from source alone (DRAFT, ready for `verify-catalogue-semantics`).
- **`dbt/models/_dq/mart_school__enrolment_summary.dq.yml`** — every test tagged by DQ dimension;
  plus the freshness/row-budget/accuracy singular tests.
- **`consumption/consumers/pnea_exams/onboarding_plan.md`** — the second consumer onboarded entirely
  by reuse, with the write-back mart planned.
- **`ops/readiness_report.md`** — the go-live gate: auto-checks (CI, runbook, rollback, DQ, RBAC,
  alerts, secrets) + attestations, all green.

## The point

One spec per step, one command per step, deterministic output, gates that compose. Generate offline,
run `dbt build`/loads/imports on the stack, commit on the workstation. This `platform-repo/` is what an
enrolment slice looks like once the pack has been run over it — the shape every later source, mart
and consumer follows.

> Note: `platform-repo/` is a committed **example**, not a live repo. A team scaffolds its own with
> `repo-scaffold` and runs the same chain on its real sources. The attestations in `readiness.yml` are
> filled with "golden-path demo" by the script, to show a passing gate; a real release fills them with
> real evidence.
