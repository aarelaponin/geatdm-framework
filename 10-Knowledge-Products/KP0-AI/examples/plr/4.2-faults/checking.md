# The discipline for checking — the page of the kind (PLR)

*One of the PLR project's four pages, read into every instruction of the kind and every review of it
by reference and never retyped (section 11 of the procedure, "The kinds of work of a project").*

**The kind.** Checking is the work that establishes one figure or one fact and reports it with its
evidence: every requirement and its goal, counted both ways (PLR-006); the incoming orchestrator's
three named claims (PLR-014); whether the exchange refuses a field PNEA has no basis for, on the
hosted build (PLR-015); how many learners appear on more than one list, and how many the prototype
catches (PLR-016). It changes nothing it checks.

**Where its faults come from.** `DISCIPLINE-the-methods-own-work.md`, items 1, 4 and 5;
`DISCIPLINE-application-design.md`, item 4; `DISCIPLINE-platform-implementation.md`, item 1.

**How this page grows.** As the page for analysis says.

---

## 1. What a session of this kind refuses

1. **To believe a check's zero before the check has been shown to fail.** A check planted with the
   fault it is named for must fail before its clean exit is evidence of anything.
2. **To report a count over a set its selection does not reach.** The set is listed first from its
   own source, and the selection set against it as a set; a count both ways gives both totals and
   names every member in one and not the other.
3. **To report a check's non-zero result as findings without reading each against the file it came
   from.**
4. **To check the running build from memory or from the source.** A check of what the application
   does ends at the real thing: the hosted build, with the switches named and set, and the run's
   output kept in a file.
5. **To change what it checks.** A defect found is reported, with its evidence, and becomes a
   candidate instruction.

## 2. What a review of this kind runs before it judges

- The figure worked out again by a route the report did not use: for PLR-016, from the fixture files
  directly; for PLR-006, the count run from the use case model's side.
- The check repeated on another member of the set (for PLR-015, another learner).
- The planted fault: the check given a case it must fail, and seen to fail.

## 3. What the orchestrator verifies before it issues an instruction of this kind

By reading:

- that the set or the fact to be checked is named with the source it is listed from, and the
  version that source stands at;
- that the instruction names the second route the review will use, so that the report cannot
  borrow it;
- for a check of the running build, that the build and its switches are named.
